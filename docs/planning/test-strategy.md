# 测试策略

测试是本项目的最高优先级约束。不得以冒烟测试代替全面回归。

## 测试金字塔

```
         ╱╲
        ╱  ╲          E2E 浏览器回归 (MCP)
       ╱    ╲         (最优先 — 每个元素点击验证)
      ╱──────╲
     ╱        ╲       Service 集成测试
    ╱          ╲      (Spring Boot Test + TestContainers)
   ╱────────────╲
  ╱              ╲    Repository / MQTT 接入测试
 ╱                ╲
╱──────────────────╲
                    单元测试（每个 Service 全覆盖）
```

## 1. 单元测试

- 框架：JUnit 5 + Mockito
- 范围：每个 Service 类，每个业务分支
- 覆盖率目标：Service 层 ≥ 90%，整体 ≥ 70%
- 重点关注：状态机流转、阈值算法、优先级排序、校验逻辑

### 必须覆盖的场景

- 设备状态机每个状态转换（6 种状态的完整矩阵）
- 工单状态机每个状态转换（待派单→已派单→...→已关闭）
- 库存阈值算法的边界值（正常/预警/售罄）
- 派单优先级计算的权重逻辑
- 各种异常输入（null、负数、超长、非预期状态）

## 2. 集成测试

- 框架：Spring Boot Test + TestContainers（PostgreSQL + Redis）
- 范围：Repository CRUD、自定义查询、MQTT 消息收发

### 测试列表

- 每个 Repository 的基本 CRUD
- 分页查询 + 排序 + 过滤
- 复杂查询（多表 JOIN、聚合）
- Redis 缓存读写 + TTL 过期
- MQTT 消息发布 + 接收 + 事件处理

## 3.  E2E 浏览器回归测试（MCP Chrome DevTools）

这是项目的核心测试手段。测试使用 Chrome DevTools MCP 工具模拟人类真实操作。

### 测试原则

1. **每一个页面上的每一个可交互元素都要点击一次**
2. 每个操作都抓取对应的网络请求验证
3. 每个操作后检查 UI 反馈是否正确
4. 截图存档每个页面的渲染结果
5. 控制台零错误日志

### 端到端业务链路测试（关键）

必须完整走通以下每条业务链路：

```
链路 1：设备上报库存 → 库存低于阈值 → 自动生成补货工单 → 派单 → 
        人员到场 → 处理完成 → 复核关闭

链路 2：设备上报故障码 → 故障分级 → 自动生成维修工单 → 派单 → 
        到场维修 → 复测 → 复核关闭

链路 3：运营经理查看总览 → 发现缺货预警 → 手动创建补货工单 → 
        派单给某人员 → 路线规划

链路 4：仓库管理员 → SKU 入库 → 设备补货出库 → 设备库存更新

链路 5：运营经理 → 选择多个站点 → 生成路线 → 人工调整顺序 → 
        保存路线 → 路线执行
```

### 测试通过标准

```
[ ] 零 JS 控制台错误
[ ] 所有 API 返回 2xx（验证每个请求）
[ ] 所有 UI 交互有正确视觉反馈
[ ] 截图对比无布局异常
[ ] 每个表单校验正常工作（必填/格式/边界值）
[ ] 全业务链路可完整闭环
[ ] Mock AI 模式正常返回（当 MS_KEY 不可用时）
```
